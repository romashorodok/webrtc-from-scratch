# Kernel E compiler 0.3 benchmark evidence

Status: preliminary evidence for [H02](cpython_native_module_compiler_hypotheses.md#h02-mypy-types-enable-profitable-unboxing-without-custom-types) and [H06](cpython_native_module_compiler_hypotheses.md#h06-escape-analysis-can-eliminate-temporary-python-objects). Neither hypothesis is accepted. This isolated result is not an adoption claim.

## Reproduction

The fresh pre-optimization baseline was captured before changing the generator:

```sh
.venv/bin/python tests/performance/benchmark_kernel_e.py \
  --pairs 7 \
  --warmup 2 \
  --duration 5 \
  --fps 30 \
  --bitrate 2000000 \
  --peers 1 \
  --mtu 1200 \
  --output benchmark-results/kernel-e-v0.3-seven-pair-baseline.json
```

Platform: macOS 13.7.8, x86_64, four logical CPUs; CPython 3.13.13 built with Apple Clang 14.0.3. Workload: deterministic null sink, one peer, 30 fps, 2 Mbit/s, MTU 1200, two-second warmup and five-second timed interval per sample. Source SHA-256: `7ff340182200648bd2de50b62e8a3989a366ffc06cfc4ed51243b526ef00cd8e`. Artifact SHA-256: `75f3b0c65ea5427c8783c2f3702d449d63928b218257bbea45fe74565d894053`.

The complete machine-readable record is [kernel-e-v0.3-seven-pair-baseline.json](../benchmark-results/kernel-e-v0.3-seven-pair-baseline.json). Raw paired results are CPU microseconds per frame, retained allocation blocks/bytes, and event-loop p99 milliseconds:

| Pair/order | Python | Native 0.3 |
| --- | ---: | ---: |
| 1 AB | 4499.493 / 570 / 565047 / 1.631 | 3485.947 / 6821 / 2653991 / 4.326 |
| 2 BA | 4258.413 / 570 / 565047 / 2.173 | 4118.220 / 6821 / 2653991 / 3.042 |
| 3 AB | 2476.473 / 570 / 565047 / 3.985 | 4533.867 / 6821 / 2653991 / 1.651 |
| 4 BA | 4392.220 / 570 / 565047 / 1.665 | 4452.493 / 6821 / 2653991 / 1.778 |
| 5 AB | 4257.087 / 570 / 565047 / 1.466 | 3954.593 / 6821 / 2653991 / 2.302 |
| 6 BA | 4138.747 / 570 / 565047 / 1.631 | 4003.013 / 6821 / 2653991 / 2.115 |
| 7 AB | 4314.500 / 570 / 565047 / 1.708 | 4375.500 / 6821 / 2653991 / 1.508 |

Median CPU was 4258.413 µs/frame for Python and 4118.220 µs/frame for native, a 3.29% reduction in this run. The run does not establish a stable improvement: dispersion is high and the required 5% CPU threshold was not reached. Allocation behavior fails decisively: native retained 11.97 times as many blocks and 4.70 times as many bytes. Frames, packets, byte counts, sequence results, and checksums were identical.

Limitations: this is an isolated, paced synthetic packetizer workload on one host, not a full media run; samples are short; `tracemalloc` observes Python allocator traffic rather than every platform allocation; the event-loop ticker is sensitive to host scheduling; no thermal or frequency controls were available. A qualifying end-to-end run requires a 30-second warmup, 120-second measurement, and five AB/BA pairs.

The result being carried forward from the preceding five-pair investigation is recorded verbatim:

> So the honest conclusion is: currently about 1.5% lower CPU in this isolated workload, but within measurement noise, with substantially worse allocation behavior. The next optimization target should be the generated `Nv` containers, tuple materialization, and repeated `PyMem_Realloc`.

## Direct-loop follow-up

After lowering `range` and `enumerate` loops without materialized iterator
tuples, the same seven-pair command was rerun. The complete record is
[kernel-e-v0.3-direct-loops-seven-pair.json](../benchmark-results/kernel-e-v0.3-direct-loops-seven-pair.json).
Median native CPU was 4413.153 µs/frame versus 4231.700 for Python (4.29%
worse). Native retained blocks fell from the baseline's 6821 to 5088, but that
was still 8.93 times Python's 570; retained bytes were 2440687 versus 565047.
The deterministic 10,000-resample paired-bootstrap 95% upper bound was
+1053.487 µs/frame. Only workload parity and the p99 limit passed. Therefore
the isolated gate failed, no end-to-end run was authorized, the transitional
backend remains version 0.3, and H02/H06 remain unaccepted.

## Allocation-arena and geometric-growth follow-up

The regression was addressed by giving generated byte and tuple builders
geometric capacity, replacing operator-name dispatch with compile-time enum
operations, and reclaiming all private-helper allocations at the public
boundary. A final seven-pair run used the same command, with the output changed
to `benchmark-results/kernel-e-v0.3-arena-reverse-seven-pair.json`:

```sh
.venv/bin/python tests/performance/benchmark_kernel_e.py \
  --pairs 7 \
  --warmup 2 \
  --duration 5 \
  --fps 30 \
  --bitrate 2000000 \
  --peers 1 \
  --mtu 1200 \
  --output benchmark-results/kernel-e-v0.3-arena-reverse-seven-pair.json
```

The source SHA-256 remained
`7ff340182200648bd2de50b62e8a3989a366ffc06cfc4ed51243b526ef00cd8e`;
the generated artifact SHA-256 was
`21eea488da4a77f67ec2c8c4f205af2b620b581a88e48a7f0c38f4ae58f47885`.
Median native CPU was 4512.133 µs/frame versus 4658.087 for Python, a 3.13%
reduction. The deterministic paired-bootstrap 95% upper bound was -6.273
µs/frame. Native retained 552 blocks and 563503 bytes versus Python's 570
blocks and 565047 bytes, so both allocation limits passed. Workload parity and
the p99 limit also passed.

This fixes the observed CPU regression and the retained-allocation regression,
but it does not reach the required 5% CPU reduction. The isolated gate therefore
still fails, no end-to-end run is authorized, compatibility remains 0.3, and
H02/H06 remain unaccepted. The generated backend also still uses `Nv` for
private aggregate values, so this result is not the completed typed 0.4 backend.
